Architecture

The Complete Pipeline

Four phases with clean contracts between them. Every phase is independently testable and replaceable. The canonical data type — ThreatVector — flows through all four.

Phase 1 · Extraction

ToolDescriptionAnalyzer + ASTExtractor

Parse Python source. Scan docstrings for hidden instructions. Walk AST for dangerous call patterns. Output: list[ThreatVector] wrapped in ScanResult.

↓
Phase 2 · KB Routing

KBRouter + YAML Rule Files

Load 9 YAML rules at startup. Match each ThreatVector to its rule by rule_id. Decide routing tier. Output: list[EnrichedFinding].

↓
Phase 3 · LLM Analysis

LLM Provider (Claude Haiku)

Only NEEDS_CONTEXT findings reach here. LLM adds one paragraph explaining how this specific code is exploitable. Skipped entirely for SELF_CONTAINED findings.

↓
Phase 4 · Reporting

Markdown + SARIF Reporters

Render enriched findings into human-readable Markdown and machine-readable SARIF (for GitHub Code Scanning). Output: audit-report.md + audit-report.sarif.

📄 Canonical Contract

  • ThreatVector — produced by every extractor
  • ScanResult — file_path + findings + parse_status
  • EnrichedFinding — vector + KB rule + routing + LLM analysis
  • All types live in threat_vector.py — one import, no circular deps

🔒 Phase Isolation

  • Each phase only knows its input and output types
  • Extractors never import from router or reporters
  • Router never imports from extractors or reporters
  • Reporters only consume EnrichedFinding — nothing else

🧪 Test Architecture

  • 18 tests — ToolDescriptionAnalyzer (corpus-driven)
  • 27 tests — ASTExtractor (corpus-driven)
  • 25 tests — KBRouter (hand-built fixtures, isolated)
  • 20 tests — LLM Reasoner (routing gate, injection safety, batch)
  • 27 tests — Reporters (Markdown + SARIF 2.1.0)
  • False-positive regression tests in every suite

Phase 1

Extractors

Two independent extractors covering different attack surfaces. Both produce the same ThreatVector schema. The pipeline treats them identically.

🎯

ToolDescriptionAnalyzer

Scans @mcp.tool() docstrings — the primary attack surface. Validated against 3 real-world exploits from Invariant Labs.

Design Challenges

  • Real exploits live only in docstrings, not function bodies — required a separate extractor class, not an AST node walker
  • Rug pull pattern is structural, not textual: must detect if os.path.exists() → __doc__ = ... across 3 AST node types
  • Regex must be case-insensitive and avoid false positives on legitimate tool docs
  • Both @mcp.tool() and @server.tool() decorator variants must be detected

Security Measures

  • All patterns validated against 3 real known-vulnerable MCP servers before shipping
  • Confidence.VERIFIED reserved for corpus-validated patterns only
  • Clean-file regression test prevents future rules from firing on benign tools
  • Patterns grouped by attack class — adding a new class can't silently alias an existing one

What Can Be Substituted

  • Regex patterns → Semgrep rules (same rule_id namespace, same ThreatVector output)
  • MCP docstring scanning → any LLM framework that exposes tool descriptions (LangChain tools, OpenAI function_call schemas)
  • Hardcoded patterns → loaded from YAML at startup for hot-reload without redeployment

Cost & Reuse

  • Zero LLM calls — pure regex + AST, deterministic
  • All 4 rules (TPA-001, TPA-002, SHADOW-001, RUGPULL-001) are SELF_CONTAINED → router skips LLM entirely
  • Stateless class — one instance, any number of files, no re-initialization
🔍

ASTExtractor

Walks the Python AST to detect dangerous call patterns in function bodies: command injection, eval/exec, secret exposure, SSRF.

Design Challenges

  • os.system vs subprocess: os.system always invokes a shell; subprocess only dangerous with shell=True — two different matching strategies for similar risk
  • os.environ[key] is a Subscript node, not a Call node — requires a separate walker branch
  • Popen without shell=True still deserves a flag (MEDIUM, EXPERIMENTAL) — attacker-controlled argv is still risky
  • Severity is HIGH not CRITICAL for most AST findings — static analysis cannot determine if input is attacker-controlled

Security Measures

  • 4 separate detector functions — each returns list[ThreatVector], none share state, failures are isolated
  • SyntaxError in target file → parse_status="failed", warning attached, no crash
  • All detectors use private helper functions (_is_attr_call, _has_shell_true) — prevents callers from bypassing matching logic
  • Evidence field captures exact call signature — no inference, auditable

What Can Be Substituted

  • AST walking → Bandit integration (same rule_ids, Bandit findings mapped to ThreatVector with source="bandit")
  • AST walking → Semgrep (source="semgrep")
  • New language support → replace ast.parse() with tree-sitter, keep same ThreatVector output
  • Add detectors: pickle.loads() (deserialization), yaml.load() without Loader, path traversal — each is one new private function

Cost & Reuse

  • Zero LLM calls — Python stdlib ast module only
  • CMI-001 and CMI-003 are SELF_CONTAINED → no LLM tokens spent
  • CMI-002, SEC-001, SSRF-001 → NEEDS_CONTEXT, LLM called only for these 3 rule types
  • Same class scans any Python file — not MCP-specific, reusable for general Python auditing

Phase 2

KB Router

Loads 9 YAML rules once at startup. Routes each ThreatVector to an EnrichedFinding with full rule content and a routing decision that controls LLM spend.

🗂

KBRouter

The gatekeeper between deterministic analysis and probabilistic LLM reasoning. Decides what's already known vs. what needs inference.

Design Challenges

  • Load-once caching: 9 YAML files read at __init__ into a dict[rule_id → rule] — O(1) lookup per finding, no per-file disk I/O
  • EnrichedFinding not ThreatVector mutation: Pydantic v2 rejects extra fields → wrapper object preserves immutability of the original vector
  • Unknown rule fallback: rule_ids not in KB get routing=NEEDS_CONTEXT, not a crash — future rules work without code changes
  • Dependency direction enforced: EnrichedFinding lives in threat_vector.py so reporters never import from router

Security Measures

  • yaml.safe_load() — never yaml.load() which allows arbitrary Python object deserialization
  • YAML files are read-only rule definitions — no executable content, no user input
  • KB directory path validated at init — prevents directory traversal if path is configurable
  • Original ThreatVector is immutable inside EnrichedFinding — downstream consumers cannot modify extraction results

What Can Be Substituted

  • YAML files → SQLite database (same interface, hot-updatable without restart)
  • YAML files → remote rules API (fetch on startup, same dict structure)
  • Routing tiers → ML classifier trained on finding + code context → outputs routing tier
  • Add new rule: drop a new YAML file in kb/, no code changes needed

Cost & Reuse

  • 6 of 9 rules are SELF_CONTAINED → 0 LLM tokens for those findings
  • In a typical scan: 80%+ findings SELF_CONTAINED (the most common patterns are the best-known ones)
  • KBRouter is stateless after init — safe to use as a singleton across all files in a scan session
  • YAML rule format is language-agnostic — same KB can serve a future TypeScript or Go extractor

Routing Tiers — Decision Criteria

Tier When to Use LLM Call? Example Rules
SELF_CONTAINED Pattern alone is unambiguous. You can write a complete accurate description without seeing the actual code. No TPA-001, RUGPULL-001, CMI-003
NEEDS_CONTEXT Finding is real but severity depends on surrounding code. Is the URL hardcoded or from user input? Yes — 1 paragraph CMI-002, SEC-001, SSRF-001
NEEDS_ANALYSIS Finding uncertain. LLM reads whole file to decide real vs. false positive. Yes — full file (future rules)
NEEDS_CHAIN Multiple findings form an attack chain. LLM connects them into a complete exploit sequence. Yes — multi-step (future rules)

Phase 3

LLM Analysis

The deliberate constraint: LLM is only called for findings where static analysis is genuinely insufficient. The architecture was designed to minimize this surface, not maximize it.

🤖

LLM Provider (Claude Haiku)

Adds one paragraph of code-specific context to NEEDS_CONTEXT findings. Populates EnrichedFinding.llm_analysis.

Design Challenges

  • Model choice: Claude Haiku vs Sonnet — Haiku is 15× cheaper, sufficient for "does this URL come from user input?" analysis
  • Prompt scope: pass only the relevant function body, not the full file — smaller context = lower cost + more focused output
  • Failure modes: LLM unavailable, rate-limited, or returns garbage → finding still output with llm_analysis=None, not dropped
  • Output contract: LLM output is freeform text stored in one field — never parsed or trusted as structured data

Security Measures

  • Routing gate in base class — SELF_CONTAINED findings never reach _call_llm(), enforced once for all providers. A future provider that forgets the check cannot bypass it.
  • XML delimiters + system prompt framing — attacker-controlled evidence is always inside <evidence> tags. System prompt explicitly labels this content as untrusted data, not instructions.
  • Raw source never sent — only extracted fields (evidence line, our descriptions, KB rule text). Privacy guarantee holds by data model, not by convention.
  • Immutable findings — model_copy() returns a new object; original llm_analysis=None is never mutated. Proven by test.
  • API key from ANTHROPIC_API_KEY env var only — never hardcoded, never logged

What Can Be Substituted

  • Claude Haiku → GPT-4o-mini, Gemini Flash — same prompt interface, swap the API client
  • Cloud LLM → local Ollama (llama3, mistral) — airgapped environments, no data leaves the machine
  • LLM entirely → disable with --no-llm flag → all findings output with llm_analysis=None, cost = $0
  • Add NEEDS_CHAIN support: multi-call chain over all findings in the file, same provider interface

Cost & Reuse

  • Only 3 of 9 rules ever trigger an LLM call (CMI-002, SEC-001, SSRF-001)
  • Claude Haiku: ~$0.00025 per 1K input tokens — analyzing one function body ≈ $0.00003
  • A 500-file CI scan with 20 NEEDS_CONTEXT findings ≈ $0.02 total
  • Provider interface is one abstract method — swapping models requires changing one class

Phase 4

Reporters

Two output formats with different audiences. Both consume the same list[EnrichedFinding] — the reporter format is a runtime flag, not an architectural decision.

📋

Markdown Reporter

Human-readable audit report. Designed for developer review, pull request comments, and email delivery.

Design Challenges

  • Severity ordering: CRITICAL findings rendered first regardless of file order
  • SELF_CONTAINED findings use KB remediation directly; NEEDS_CONTEXT findings prepend LLM analysis paragraph
  • Evidence field rendered as inline code — never interpolated into shell commands or SQL
  • Summary table at top for quick triage — counts by severity, not just a flat list

Security Measures

  • All finding fields rendered as escaped Markdown — no raw HTML injection from LLM output
  • File paths in output are relative — absolute paths not written to reports (information disclosure)
  • LLM analysis output sanitized before rendering — script tags, HTML stripped
  • Report written to file, not stdout by default — prevents accidental credential exposure in CI logs

What Can Be Substituted

  • Markdown → HTML report with syntax-highlighted code snippets
  • File output → GitHub PR comment via API (same EnrichedFinding input)
  • Markdown → Jira ticket creation, Slack webhook, PagerDuty alert
  • All reporters share the same interface — adding a new format is one new class

Cost & Reuse

  • Zero external dependencies — Python stdlib only (pathlib, string formatting)
  • Idempotent: same input always produces same output — safe to re-run in CI
  • Stateless: reporter class has no init state, safe as a singleton
🔗

SARIF Reporter

Static Analysis Results Interchange Format — the standard for CI/CD integration. Natively supported by GitHub Code Scanning, VS Code, and Azure DevOps.

Design Challenges

  • SARIF requires physical locations with URI + line number — ThreatVector location field parsed to extract these
  • Rule metadata (id, name, help text) lives in runs[].tool.driver.rules[] — populated from KB YAML, deduplicated
  • OWASP LLM mapping in ThreatVector must translate to SARIF tags array
  • GitHub Code Scanning requires specific SARIF 2.1.0 schema — validation against schema before output

Security Measures

  • SARIF is JSON — all string values escaped, no raw finding text interpolated unsafely
  • File URIs in SARIF use relative paths — absolute paths not written (avoids leaking directory structure)
  • SARIF output validated against schema before writing — malformed output caught before CI ingestion
  • LLM analysis stored in SARIF message.markdown field — never in fixes or executable fields

What Can Be Substituted

  • SARIF → JUnit XML (for Jenkins/TeamCity compatibility)
  • SARIF → CodeClimate JSON (for GitLab CI)
  • SARIF → direct GitHub Check Annotations API — inline PR comments on the exact line
  • Same EnrichedFinding input, different serialization — reporter interface unchanged

Cost & Reuse

  • SARIF integrates with GitHub Code Scanning for free — findings appear as PR annotations without any additional tooling
  • One scan produces both reports simultaneously — no second pass needed
  • SARIF output consumable by any SAST dashboard (DefectDojo, SonarQube, etc.)

Economics

How We Save Costs

Every architectural decision was made with LLM cost in mind. The goal: spend zero tokens on findings that don't need reasoning, and spend minimal tokens on those that do.

Rules are SELF_CONTAINED

Design Principles

How We Made It Reusable

Every substitutable component was identified during design and isolated behind a clean interface. The architecture supports MCP servers today — and any Python codebase, any LLM framework, any output format tomorrow.

ThreatVector as Universal Contract

Every extractor speaks the same language. Add a Semgrep extractor, a Bandit adapter, or a TypeScript AST walker — as long as it produces ThreatVector objects, the rest of the pipeline works unchanged.

KB as Plain YAML

Adding a new rule is dropping a file. No code changes. No redeployment. The router discovers new rules at startup automatically. The YAML format is language-agnostic — the same KB can be shared with a future Go or Rust scanner.

LLM Provider Interface

Abstract base defines analyze(finding) → EnrichedFinding. The routing gate (skip SELF_CONTAINED) lives in the base class — subclasses implement only _call_llm(). Swapping Claude for GPT-4o-mini, Gemini, or local Ollama is one new class; the security invariant cannot be bypassed.

Reporter Interface

Both reporters implement the same interface: render(findings) → str. Adding a Slack webhook reporter, a Jira integration, or an HTML dashboard is one new class that no existing code needs to know about.

Routing Tier Extensibility

The 4-tier routing schema (SELF_CONTAINED → NEEDS_CONTEXT → NEEDS_ANALYSIS → NEEDS_CHAIN) was designed for where the architecture needs to go, not just where it is today. Adding multi-step chain analysis is a new tier in the existing field.

source Field on ThreatVector

Every finding declares its origin: "native" | "semgrep" | "bandit". A Bandit adapter can produce ThreatVectors with source="bandit" — the reporter renders them identically, but provenance is preserved for auditing.
